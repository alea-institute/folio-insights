<objective>
Ship online collision detection at mint via a global content-addressed
`shard_iri_registry` (D-04) with a fail-closed halt+flag fallback (D-03), prove
it at 100K shards (D-05/SHARD-08), and add the `folio-insights verify-iris`
nightly re-hash CLI (D-06/D-07).

Purpose: at hex32 the collision path is effectively unreachable, but SHARD-08
demands it exist and be exercised. The registry detects the never-expected case
deterministically (same body + different full hash → collision) and refuses to
mint rather than silently overwriting provenance. `verify-iris` is the standing
guard against source drift or a hash-logic regression: re-mint every stored
shard and surface any mismatch for human review with a non-zero exit.

Output: new `shards/iri_registry.py` (global SQLite store + `ShardIRICollision`),
a `verify-iris` Click command in `cli.py`, and the SHARD-08 collision + CLI tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mint path → shard_iri_registry | concurrent writers may register colliding hex32 bodies; the collision-check + insert must be a single transaction / UNIQUE-constrained |
| stored source_uri/source_span → verify-iris | the CLI reads back attacker-influenced extracted text (URIs, spans) and re-mints; must treat as data, never as SQL/shell |
| CLI args (--db path) → filesystem | operator-supplied DB path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04 | Tampering | shard_iri_registry collision branch | mitigate | Fail closed (D-03): same hex32 body + different full hash → `raise ShardIRICollision`, log both hashes, NEVER UPDATE/overwrite the existing row. Refusing to mint prevents a colliding shard from silently clobbering an existing provenance record. |
| T-04-05 | Tampering | registry SQL | mitigate | All registry SQL parametrized with `?` placeholders (aiosqlite, no string interpolation) — SQL-injection-safe even though source_uri/source_span originate from untrusted extracted text. |
| T-04-06 | Elevation/Race | concurrent mint collision check | mitigate | `iri_body TEXT NOT NULL UNIQUE` constraint makes the insert atomic at the DB layer: a racing duplicate-body insert fails the UNIQUE constraint rather than producing two rows; the register() read-then-insert resolves to idempotent-or-collision. Document the UNIQUE invariant as the race guard. |
| T-04-07 | Repudiation | verify-iris re-hash job | mitigate | verify-iris is the standing re-hash audit (D-06): a stored IRI that no longer re-mints from its source flags drift/regression with a non-zero exit + logged report (D-07) for human review — does NOT auto-quarantine (no destructive action on detection). |
| T-04-08 | Denial of service | 100K / large-corpus verify scan | accept | verify-iris is a nightly batch job, not a request-path surface; large-N scan time is acceptable for an offline audit. Heavier scheduling/alerting deferred to Phase 12 per D-07. |

No npm/pip/cargo installs in this plan (aiosqlite + click already in deps) → package legitimacy gate N/A (no `T-04-SC`).
</threat_model>
