# Phase 3.5: Railway Dev/Testing Server - Research

**Researched:** 2026-05-22
**Domain:** Railway PaaS deployment (CLI v4.31.0, config-as-code, GitHub auto-deploy, 502 diagnosis)
**Confidence:** HIGH (CLI surface verified against the installed binary; config-as-code + 502 causes verified against current official docs)

## Summary

This phase restores a working Railway dev deployment of v2.0 `master` at the existing
`folio-insights-production.up.railway.app` URL and wires auto-deploy on push to `master`.
Authentication is human-gated (`railway login` is an interactive browser/device pairing that
an agent cannot script), so the first task must surface that step to the operator before any
diagnosis runs.

The single most important finding: the **current `railway.toml` is structurally invalid for
Railway's config-as-code schema**. Railway's documented config-as-code schema is *flat*
(top-level `build`, `deploy`, `environments` tables) and applies to **one service per file,
resolved from that service's connected root directory**. The repo's
`[services.web]` / `[services.worker]` *nested* layout is an **open feature request, not
supported functionality** `[VERIFIED: docs.railway.com/config-as-code/reference + station.railway.com feedback thread]`.
A nested-services TOML is silently ignored by the deployer — which means the committed
healthcheck, builder, and dockerfilePath are NOT being applied. This is a strong candidate for
(or major contributor to) the 502, alongside the CONTEXT.md hypothesis that the two-service
split no longer matches the single legacy service the v1.1 deploy created.

The second important finding: `ci/railway.py` invokes `railway up --service X --image Y`, but
**`railway up` has no `--image` flag in v4.x** (verified against the installed binary). The
image-deploy path in v4.x is `railway add --image <IMAGE>` (sets a service's source to a
registry image); `railway up` only builds-and-deploys the uploaded directory. The
`ci/railway.py` `--image` branch is dead/broken for the installed CLI and the planner should
flag it (but fixing CI is arguably Phase 20 scope — see Open Questions).

**Primary recommendation:** Treat this as a *config-correction + reconnect* job, not a fresh
deploy. After human `railway login`, link to the existing project, diagnose with
`railway logs --build` / `railway logs --deployment` / `railway variables`, then (almost
certainly) **collapse `railway.toml` to a single flat web-tier config** (no `[services.*]`
nesting) so config-as-code actually applies, confirm the service's GitHub source points at
`master`, and redeploy. Keep the worker out of the dev environment entirely (it is an idle stub
until Phase 10).

## Railway CLI v4.31.0 — Verified Command Surface

All of the following were captured from `railway <cmd> --help` on the **installed v4.31.0
binary** `[VERIFIED: railway --help]`. This supersedes any training-data recollection of v3.x.

### Authentication (human-gated)
```bash
railway login                 # interactive browser pairing (opens a browser, confirm code)
railway login --browserless   # prints a URL + pairing code for headless/SSH; STILL requires
                              #   a human to open the URL and confirm — NOT scriptable by an agent
railway whoami                # confirm logged-in user (currently: "Unauthorized" — logged out)
railway logout
```
- **There is no password/token argument to `login`.** Non-interactive auth uses env vars
  instead: `RAILWAY_TOKEN` (project/environment-scoped, deploy actions) or `RAILWAY_API_TOKEN`
  (account/workspace-scoped). `[CITED: docs.railway.com/guides/cli]`
- The first task MUST be `autonomous: false` and surface `! railway login` to the operator.
  After the operator logs in, the agent's subsequent `railway` calls in the same shell session
  inherit the credential. `[VERIFIED: railway login --help shows only -b/--browserless]`

### Link to the existing project
```bash
railway link                                  # interactive: pick workspace → project → env → service
railway link -p <PROJECT> -e <ENVIRONMENT> -s <SERVICE>   # non-interactive once names are known
railway status [--json]                       # show linked project / environment / service
railway service status                        # deployment status for services in the project
railway environment                           # list/switch environments (aliases: env)
railway list                                  # list all projects in the account
railway unlink                                # disassociate the directory
```
- `railway link` writes link state to a local config (a `.railway` association); `railway status`
  reads it back. The repo currently has **no `.railway` link** `[VERIFIED: ls .railway → absent]`.

### Diagnose the 502
```bash
railway logs --build [-n 200]                 # build logs (did the image build at all?)
railway logs --deployment [-n 200]            # runtime/deploy logs (crash, missing env, wrong port?)
railway logs --latest                         # logs from the latest deploy even if it failed/building
railway logs --json -n 200                    # structured logs for parsing
railway variables list [--kv] [--json]        # what env vars the service has (cross-check .env.docker.example)
railway status --json                         # topology: which services/environments exist
```
- `-d/--deployment` and `-b/--build` are the two log views. Both accept `-n/--lines`,
  `--since`, `--until`, `-f/--filter` (e.g. `@level:error`), and `-s/--service`.
  `[VERIFIED: railway logs --help]`

### Set runtime variables (secrets)
```bash
railway variable set KEY=value -s web                 # preferred (modern) form
railway variable set KEY=value --skip-deploys -s web  # set without triggering a redeploy
railway variable set TOKEN --stdin -s web             # read secret value from stdin (avoids shell history)
# Legacy (still works but deprecated):  railway variables --set "KEY=value"
```
- Aliases: `railway variable | variables | vars | var`. `--set` on the parent `variables`
  command is **legacy**; the modern path is the `variable set` subcommand. `[VERIFIED: railway variable set --help]`
- Use `--stdin` for `RAILWAY_TOKEN`/LLM keys so secrets never hit argv or shell history
  (consistent with T-00-19).

### Deploy
```bash
railway up [-s web] [-c] [-d] [-e <env>] [-p <proj>]   # build & deploy the CURRENT DIRECTORY
railway redeploy -s web [-y]                            # redeploy the latest build (no re-upload)
railway restart -s web                                  # restart latest deployment WITHOUT rebuilding
railway add -i <IMAGE> -s <name>                        # create/point a service at a prebuilt registry image
railway add -r alea-institute/folio-insights -s web     # create a service connected to a GitHub repo
railway down                                            # remove the most recent deployment
railway domain [-s web]                                 # show/generate the *.up.railway.app domain
```
- `railway up` flags (verified): `-d/--detach`, `-c/--ci` (stream build logs only, then exit),
  `-s/--service`, `-e/--environment`, `-p/--project`, `--json`, `-m/--message`.
  **There is NO `--image` flag on `up`.** `[VERIFIED: railway up --help]`
- `railway redeploy` flags: `-s/--service`, `-y/--yes`, `--json`. `[VERIFIED: railway redeploy --help]`
- `railway add` flags include `-i/--image`, `-r/--repo`, `-s/--service`, `-d/--database`,
  `-v/--variables`. This is the v4.x home of image and GitHub-repo wiring. `[VERIFIED: railway add --help]`
- `railway deploy` is **template provisioning only** (`-t/--template`), NOT an app deploy. Do
  not confuse with `up`. `[VERIFIED: railway deploy --help]`

### Pattern 1: Flat single-service config-as-code (the fix)
**What:** Railway's config-as-code schema is flat. The deployer expects top-level `[build]`,
`[deploy]`, `[environments.*]` tables, applied to the one service whose root directory contains
the file. `[CITED: docs.railway.com/config-as-code/reference]`
**When to use:** This phase, for the web-only dev deploy.
**Example (replacing the current nested toml):**
```toml
# railway.toml — flat schema, applies to the connected web service
# Source: docs.railway.com/config-as-code/reference
[build]
builder = "DOCKERFILE"
dockerfilePath = "Dockerfile.web"

[deploy]
healthcheckPath = "/health"
healthcheckTimeout = 120
restartPolicyType = "ON_FAILURE"
restartPolicyMaxRetries = 3
```
> NOTE: The planner must confirm during diagnosis whether the *worker* service must be
> preserved in this same repo for Phase 20. If so, the long-term answer is the Railway
> *monorepo* pattern (each service rooted in its own directory with its own config file), not a
> nested single file. For the dev server, web-only flat config is the minimal correct change.
> The exact field set above mirrors what is already in the repo — only the `[services.web]`
> nesting is removed.

### Pattern 2: Auto-deploy on push to `master`
**What:** Connect the web service's source to the GitHub repo and set trigger branch `master`;
every push rebuilds. `[CITED: docs.railway.com/deployments/github-autodeploys]`
**When to use:** Locked decision for this phase.
**How:**
- Connecting a *new* service to a repo: `railway add -r alea-institute/folio-insights -s web` (CLI).
- For the *existing* service, set/confirm the source + **trigger branch** in the dashboard:
  Service → Settings → Source → connect repo → trigger branch = `master`.
- Requires: a project member with a connected GitHub account that has contributor access, and
  the Railway GitHub App installed on `alea-institute/folio-insights` with no pending permission
  updates. `[CITED: docs.railway.com/deployments/github-autodeploys]`
- Optional: "Wait for CI" pauses the deploy until a matching `on: push` GitHub workflow passes
  (deploys enter `WAITING`; failed workflow → `SKIPPED`). Not required for the dev server.

### Anti-Patterns to Avoid
- **Nested `[services.web]`/`[services.worker]` in one `railway.toml`:** unsupported; silently
  ignored. The committed healthcheck/builder never applies. (Root-cause candidate for the 502.)
- **`railway up --image`:** no such flag on v4.x; use `railway add --image`.
- **Creating a new project/service:** violates the locked "reuse existing service/domain" decision.
- **Committing `RAILWAY_TOKEN` or LLM keys:** always masked Railway variables (T-00-19).
- **Pulling the worker into the dev deploy:** it is an idle stub (Phase 10); doubles build time
  and image cost for no benefit at Phase 3.

## Common Pitfalls

### Pitfall 1: Nested-services `railway.toml` is silently ignored
**What goes wrong:** The committed `[services.web]`/`[services.worker]` config never applies, so
the healthcheck (`/health`, 120s), builder, and `dockerfilePath` are not enforced on the
deploy. Railway falls back to dashboard/auto-detected settings, which may build the wrong thing
or skip the healthcheck.
**Why it happens:** Railway config-as-code is flat (`build`/`deploy`/`environments`); nested
`[services.NAME]` is an open feature request, not implemented. `[VERIFIED: docs reference + station feedback thread]`
**How to avoid:** Collapse to a flat single-service `railway.toml` (Pattern 1) for the web
service. Confirm via `railway logs --build` that the build used `Dockerfile.web`.
**Warning signs:** Build logs show Railpack/auto-detection instead of `Dockerfile.web`; deploy
goes "healthy" with no healthcheck wait; the live URL 502s.

### Pitfall 2: `ci/railway.py --image` path is broken on CLI v4.x
**What goes wrong:** `railway up --service X --image Y` errors — `up` has no `--image` flag.
**Why it happens:** The wrapper was written against "railway-cli >= 3.x" (comment line 41). v4.x
moved image-deploy to `railway add --image`.
**How to avoid:** This phase uses GitHub-source builds (`railway up`/auto-deploy without
`--image`), so the broken branch is not on the critical path. The planner should still note it
and decide whether to fix `ci/railway.py` now (swap to `railway add -i`) or defer to Phase 20.
**Warning signs:** Any manual `python -m ci.railway web <image_ref>` invocation fails.

### Pitfall 3: Wrong public domain target port → 502
**What goes wrong:** The edge proxy routes the domain to a port the container isn't listening
on, producing a 502 even when the app is healthy.
**Why it happens:** Domain target port (dashboard state) drifted from the app's `$PORT` (8000).
**How to avoid:** `Dockerfile.web` correctly binds `0.0.0.0:$PORT` (verified). In diagnosis,
confirm the service's public domain target port matches; Railway can usually infer it from
`EXPOSE 8000` + `$PORT`, but verify. `[CITED: docs.railway.com/networking/troubleshooting/application-failed-to-respond]`
**Warning signs:** Response carries `X-Railway-Fallback: true`; deploy logs show the app started
fine but the URL still 502s.

### Pitfall 4: Large image (~8.7 GB) build timeout / storage limit
**What goes wrong:** torch + CUDA via `sentence-transformers` make the web image huge; first
build takes 10-15 min and may hit Railway build-time or storage limits.
**Why it happens:** GPU torch wheels are pulled by default.
**How to avoid:** README already documents the lever — pin **CPU-only torch** in
`Dockerfile.web` (the dev server has no GPU). Decide in Stage 1 only if builds actually time
out; don't pre-optimize. `[VERIFIED: README §Notes line 340-342]`
**Warning signs:** Build log stalls during pip/uv install of torch; build killed at a time cap.

### Pitfall 5: Suspended / usage-capped service masquerading as a 502
**What goes wrong:** A trial-expired or usage-capped service returns edge errors with no healthy
container, indistinguishable at the URL from a crash-loop 502.
**Why it happens:** Account/plan limits, not code.
**How to avoid:** `railway status` + dashboard surface suspension immediately in Stage 0/1.
Rule this out before touching config. `[CITED: RAILWAY-DEV-SERVER-PLAN.md risks]`
**Warning signs:** `railway status` shows a suspended/limited state; no recent deploys exist.

### Pitfall 6: Auto-deploy trigger branch still on the v1.1 shape
**What goes wrong:** The service rebuilt on a push to `master` against config that no longer
matches the single legacy service (CONTEXT.md leading hypothesis) — or the branch wiring/source
is stale.
**Why it happens:** v1.1 connected a single-service source; v2.0 changed `railway.toml` shape.
**How to avoid:** Confirm/reset Source → trigger branch = `master` AFTER the flat toml fix, so

**Warning signs:** Latest deploy timestamp matches a recent `master` push but the build used the
