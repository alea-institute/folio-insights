- Local `railway` CLI is **v4.31.0** and **logged out**; no `.railway` link in the repo.
- `fixtures/bench.nq` (235 MB) is now git-ignored and regenerable — not bundled into deploys.

**Out of scope:** Multi-environment promotion, the worker's real Arq consumer (Phase 10), production hardening, custom domains, the Phase 20 GA cut.

<decisions>
## Implementation Decisions

### Diagnose before scoping (LOCKED)
- First task **must** be diagnosis against the live Railway project: authenticate, link, read deploy/build logs and variables, and determine the real 502 cause and current service topology.
- **Only after** diagnosis, choose deploy scope: **web-only** (likely — worker is an idle stub at Phase 3) vs **web + worker**. Do not pre-commit to scope in the plan; make it a decision gate informed by findings.

### Auto-deploy on master (LOCKED)
- Wire the Railway service GitHub source to branch `master` so every push triggers a redeploy.

### Reuse existing service/domain (LOCKED)
- Restore the existing service and its `*.up.railway.app` URL rather than provisioning new infrastructure.

### Authentication is human-gated
- `railway login` is interactive (device/browser flow) and **cannot** be automated by an agent. The first task is `autonomous: false` — it must surface the `! railway login` step to the operator.
- `RAILWAY_TOKEN` and any LLM/API keys are set as **masked Railway variables**, never committed (consistent with `ci/railway.py` T-00-19 handling).

### Claude's Discretion
- Whether to pare `railway.toml` to web-only for the dev environment vs leaving the worker service uncreated.
- Exact env-var set the `web` tier needs (derive from `.env.docker.example` / `.env.example` during diagnosis).
- How to handle the ~8.7 GB image size if builds time out (README notes CPU-only torch as the lever).
</decisions>
