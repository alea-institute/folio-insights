## Root cause

The 502 has **two compounding causes** (the planning hypothesis was correct about the toml, but the
*immediate* build failure is concrete and was confirmed from live build logs):

1. **Enabling cause — nested `railway.toml` is silently ignored.** The committed config uses nested
   `[services.web]` / `[services.web.build]` / `[services.worker]` tables. Railway's config-as-code does
   **not** support that nested schema, so it is dropped without error. Proof: the live deployment's
   resolved `serviceManifest` shows `dockerfilePath = "/Dockerfile"` (NOT `Dockerfile.web`),
   `healthcheckPath = null` (NOT `/health`), `restartPolicyMaxRetries = 10` (NOT the `3` the toml
   specifies). None of the toml's nested values applied — Railway fell back to the dashboard/auto
   default of `/Dockerfile`.

2. **Immediate cause — the stale `/Dockerfile` fails to build.** Railway therefore builds from the v1.1
   leftover `/Dockerfile` (dated Apr 12, predates the v2.0 web/worker split). That file does
   `COPY output/ ./output/` (line 53), but `.dockerignore` line 24 (`output`) excludes the entire
   `output/` directory from the Docker build context. The latest deploy (commit `c4d84ec`, branch
   `master`) failed with:

   ```
   [ERRO] [stage-1 10/11] COPY output/ ./output/
   Build Failed: failed to compute cache key: failed to calculate checksum of ref ...: "/output": not found
   ```

   Build fails → no healthy replica → the Railway edge returns **HTTP 502** with header
   `x-railway-fallback: true` on `/`, `/health`, and `/api/v1/corpora` (all confirmed live, 2026-05-22).

**Latest deployment:** id `251b2e40-10a1-42c7-a192-38e03dd4cf01`, status **FAILED**, commit `c4d84ec`
("docs(03.5): create phase plan"), configFile `/railway.toml`, repo `alea-institute/folio-insights`,
runtime V2, plan `hobby`. An earlier deploy was healthy (build logs show a `/Dockerfile` build with the
`/health` healthcheck succeeding and traffic served on `/api/v1/*`) before being terminated by this
failed redeploy.

## Why the Plan 02 fix resolves it (verified, not assumed)

Flattening `railway.toml` to a top-level `[build]`/`[deploy]` web-only config makes config-as-code
engage and pins `dockerfilePath = "Dockerfile.web"`. Verified the switch will build **and** boot:

- `Dockerfile.web` does **not** `COPY output/` at all → the missing-context error cannot occur. ✓
- App startup `lifespan` → `load_extraction()` is **graceful**: a missing `extraction.json` returns
  `{"corpus": ..., "units": [], "total_units": 0}` (api/main.py:99–102), so `/health` returns 200 even
  with no bundled corpora. ✓
- No LLM client initializes at import/startup (resolves Assumption A2); `lifespan` only calls
  `load_extraction()`. The web tier serves `/health` and `/api/v1/corpora` without any LLM key. ✓

## Consequence to flag for Plan 02 / Plan 03 (decision needed)

`Dockerfile.web` bundles **no corpora**, unlike the v1.1 `/Dockerfile` (which `COPY output/`). Default
`_output_dir = Path("./output")`, `_default_corpus = "default"` (api/main.py:79–80). On a restored
`Dockerfile.web` container the dir is absent, so `/api/v1/corpora` returns `[]` and the SSR viewer
renders **empty**. This collides with Plan 03's acceptance ("viewer renders the bundled corpora").
Decision for Plan 02: either (a) accept an empty dev viewer (pure 502→healthy restore, web-only scope
honored, no extra files touched), or (b) bundle corpora by adding `COPY output/ ./output/` to
`Dockerfile.web` **and** un-ignoring `output/default|demo|test1` in `.dockerignore` (mirrors the
`.gitignore` `!output/...` whitelist). Option (b) expands Plan 02 beyond its declared
`files_modified: [railway.toml, ci/railway.py]` and needs operator sign-off.

## Domain target-port finding

Port is dynamic: Railway injects `$PORT`; `Dockerfile.web` binds `uvicorn ... --port ${PORT:-8000}` and
`EXPOSE 8000`. The prior healthy deploy proved port routing works, and the current failure is at
**build** (it never reached runtime), so a wrong domain target-port (Pitfall 3) is **NOT** a cause.
Post-redeploy, confirm `curl -sI "$URL/"` returns 200 with **no** `x-railway-fallback: true` header to
re-validate the target port end-to-end.
